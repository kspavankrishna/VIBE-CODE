# Streaming Patch Hunk Applier

Every AI coding agent eventually has to turn a block of generated diff text into real changes on disk, and the naive way of doing that quietly corrupts files the moment the model gets a line number wrong. This is a dependency free Crystal CLI that parses unified diffs as they stream in and applies each hunk with fuzzy context matching, hash based staleness checks and atomic writes, so a wrong guess fails loudly instead of landing in the wrong place.

## What this solves

If you have built or used a coding agent (Claude Code, Cursor, Aider, Continue, or your own harness), you already know the pattern: the model reads some files, decides on an edit, and streams back a unified diff instead of rewriting the whole file. That diff has to be turned into a real change on disk, and this step is far more dangerous than it looks.

The classic Unix `patch` command was built for diffs generated by `diff` itself, where the line numbers in the `@@` header are always correct because a deterministic algorithm produced them. An LLM is not a deterministic diff algorithm. It counts lines in its head while generating tokens, and it gets that count wrong constantly, especially on longer files or after the file has drifted slightly from what the model last saw. When `patch` or `git apply` hit a hunk whose declared line number does not match the file, they either reject the whole hunk or fall back to a fuzz factor that can silently apply the change several lines away from where it belongs. Either outcome is bad: a rejected hunk stalls the whole agent turn, and a silently misapplied hunk can corrupt a file in a way nobody notices until CI breaks or, worse, until it ships.

There is a second problem underneath the first one. Coding agents often apply several file edits from one model response, and if hunk three of five fails, you need to know whether hunks one and two already landed on disk in a half finished state. Most naive apply scripts just loop over hunks and write as they go, so a failure partway through leaves the working tree in a state that matches neither the old code nor the new code. And a third problem: by the time the diff comes back from the model, the file on disk might have changed again if another agent, a human, or a background formatter touched it. Applying a diff against content it was never generated against is a data loss bug waiting to happen, and nothing in a plain unified diff format tells you that has happened.

Streaming Patch Hunk Applier is built to make all three of those failure modes explicit instead of silent: wrong line numbers get resolved with a bounded, honest fuzzy search that refuses to guess when it is not confident, a whole file's hunks apply as one unit that either lands cleanly or does not touch the file at all, and an optional sha256 check on the original content catches the case where the file moved out from under the diff.

## Why I built it

I kept seeing the same failure shape across different agent setups: an LLM streams back a diff, the harness shells out to `patch -p1` or hand rolls a line splice, and once every so often a hunk lands three lines off because the model miscounted a blank line inside a function. Nobody catches it right away because the file still parses and the tests that exist still pass, and it surfaces days later as a mystery bug. I wanted an apply layer that treats this as the normal case to design for, not the exception, and that gives a coding agent (or a human reviewing agent output) a structured, honest answer about exactly where each hunk landed and how much it had to guess to get there.

## When to use it

Reach for this when you are building or operating any tool that takes LLM generated unified diffs and needs to land them on real files: an agentic coding harness, a CI bot that applies suggested fixes, a review tool that previews a model's proposed patch before a human approves it, or a batch pipeline that rewrites many files from one prompt. It is also useful as a standalone safety net in front of an existing agent pipeline, since it reads a diff from a file or from standard input and never needs to know anything about how the diff was produced.

It is not a replacement for `git apply` when you are dealing with diffs from `git diff` or `git format-patch` themselves, since those already have correct line numbers and you gain nothing from the fuzzy tolerance. It is specifically for diffs whose line numbers cannot be trusted at face value.

## How it works

The whole program lives in one file, under the `StreamingPatchHunkApplier` module, split into small pieces that each own one concern.

`DiffParser.parse_stream` reads an `IO` line by line and calls the block you give it with a finished `FileDiff` as soon as one file's `---`/`+++`/`@@` section is complete, rather than waiting for the entire diff to arrive. That matters when a diff is coming straight off a live model stream: the parser can hand a completed file over to the rest of the pipeline while the model is still writing hunks for the next file. Inside a hunk, `LineKind` tags each line as `Context`, `Add` or `Remove` based on its leading character, and a `Hunk` exposes `old_block` (context plus removed lines, the text that should already exist in the file) and `new_block` (context plus added lines, what should exist after). Deliberately, the parser never trusts the hunk header's declared line counts, only the actual `+`/`-`/` ` prefixed lines that follow it, because a model that miscounts the `@@` numbers usually still gets the actual content lines right.

Locating each hunk is `HunkLocator.locate`. It first tries an exact match of `old_block` against the file, searching outward from the declared position (`old_start` minus one) in an expanding ring up to `DEFAULT_WINDOW` lines each direction, so the closest exact match always wins over a farther one. If nothing matches exactly, it retries with trailing whitespace stripped from every line, which catches the common case of a model dropping trailing spaces. If that still fails, it scores every candidate position in the window by the fraction of lines that match after stripping whitespace, and accepts the best one only if it clears `FUZZY_THRESHOLD` (0.85) and is not tied with another equally good position. A hunk with no context at all (a pure insertion) skips all of that and trusts the declared position directly, since there is nothing to verify it against; every `Match` this produces carries a `FuzzLevel` of `Exact`, `Shifted`, `Whitespace` or `Fuzzy` so the report always tells you how much trust was involved. When nothing clears the bar, it raises `HunkLocator::NoMatch` with a hint pointing at the closest thing it found, instead of guessing.

`PatchApplier.apply_file_diff` takes a `FileDiff` and the file's current content (or `nil` for a brand new file) and does the actual splice. It locates every hunk, sorts them by where they actually landed rather than the order they appeared in the diff, checks that no two hunks overlap once located, and only then builds the new content by walking the original lines and substituting `new_block` at each matched offset. File creation, deletion and the "no newline at end of file" marker are all handled as their own cases, and creation refuses to run if a file already exists on disk. `PathSafety.resolve!` checks every target path against the destination root before anything touches disk, rejecting absolute paths and any path that would resolve outside the root, since diff paths are effectively attacker or model controlled input.

Writes only ever happen through `CLI.write_result`, which writes new content to a temp file in the same directory with `File.tempfile` and then calls `File.rename` to swap it into place, so a crash mid write never leaves a half written file behind. In the default atomic mode, `CLI.run` computes every file's result first and only starts writing once it knows every file in the diff succeeded; pass `--per-file` to instead write each file the moment it succeeds, so unrelated files are not held hostage by one bad hunk.

## Usage

Build it once with the Crystal compiler:

```
crystal build --release StreamingPatchHunkApplier.cr -o patch-apply
```

Then feed it a unified diff on standard input, pointed at the root of the tree you want to patch:

```
./patch-apply --dir path/to/repo < change.patch
```

Useful flags: `--dry-run` computes and reports everything without writing anything, `--per-file` switches from all-or-nothing to independent per file writes, `--window N` widens or narrows the fuzzy search radius from its default of 200 lines, `--diff-file FILE` reads the diff from a file instead of stdin, and `-o FILE` writes the JSON report to a file instead of stdout. The staleness guard takes a repeatable `--expect PATH=SHA256` flag, or a `--expect-file manifest.json` pointing at a JSON object mapping paths to expected sha256 hashes; either way, if the file on disk does not hash to what you told it to expect, that file's hunks are refused before any matching is even attempted.

The program always prints a JSON report describing what happened: for every file, the action taken (`modified`, `created` or `deleted`), the sha256 of the content before and after, whether the result keeps a trailing newline, and for every hunk the line it matched, the fuzz level used and a confidence score. Failures list the path and the exact reason. Exit code 0 means everything applied, 1 means a configuration or diff parsing problem, 2 means one or more hunks could not be applied, and 3 means a path safety violation was caught, which is worth treating differently in a CI pipeline since it usually points at a prompt injection or a malformed diff rather than an ordinary miscount.

## Notes

The fuzzy matcher assumes LF line endings. A CRLF file will still match through the whitespace normalized pass since a carriage return counts as trailing whitespace, but any line a hunk touches will come out as LF in the result, so a CRLF repository should normalize line endings before running this, the same way you would before running most text tooling. Pure insertion hunks (no context lines at all) are trusted at their declared position since there is nothing to verify them against, so keep at least one line of context around insertions in whatever generates your diffs if you want a location guarantee rather than a best effort placement. Deletion diffs must carry the full removed content in a single hunk so the tool can confirm the file matches before deleting it; a diff that just says "delete this file" with no content is rejected on purpose. None of this depends on git, so it works just as well against a plain directory as it does inside a repository.
