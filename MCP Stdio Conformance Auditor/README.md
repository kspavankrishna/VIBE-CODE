# MCP Stdio Conformance Auditor

You wrote an MCP server. It answers `tools/list` in a demo, Claude Code or your own agent runner picks it up, and everything looks fine until it doesn't: a hang nobody can explain, a stray print statement that corrupts the whole session, a process that refuses to die when the client is done with it. This is a single Perl file that spawns your server over stdio, drives it through the handshake and fourteen adversarial checks, and tells you exactly which one it failed and why.

**Language:** Perl | **Lines:** 784 | **Added:** 2026-09-20

## What this solves

The Model Context Protocol stdio transport looks trivial on paper. Read newline delimited JSON from stdin, write newline delimited JSON to stdout, keep logs on stderr. In practice almost every hand rolled implementation gets some part of it wrong, and the wrong part is never obvious from a quick manual test because a manual test is exactly the one case where the bug does not show up.

A few examples that are common enough to have their own names once you have seen them a couple of times. A server prints a startup banner like "Server listening" straight to stdout before the client ever sends `initialize`, because the author copied a snippet from a web server tutorial where stdout was just a log. The client reads that line, tries to parse it as JSON-RPC, and either crashes or silently drops the session depending on how defensively it was written. A server pretty prints its JSON responses because that is the default in whatever library it used, so a single logical message is split across eight physical lines, and any client that reads stdout line by line (which is what the NDJSON framing promises it can do) desyncs immediately. A server answers a `notifications/initialized` message with a JSON-RPC response even though notifications have no id and are not supposed to get one back, which means the client either ignores the extra line (lucky) or matches it against the wrong pending request (a very confusing bug that shows up as an agent reporting the result of a call it never made). A server closes down fine when you Ctrl-C it in a terminal but ignores stdin EOF entirely, so under any framework that spawns a fresh MCP process per session and closes stdin to signal "we're done," the process becomes an orphan that sits there until something kills it by hand.

None of these are exotic. They are the direct result of MCP servers being built on every language and stack imaginable, glued onto stdio as an afterthought, with nobody running a real conformance suite against the transport layer before shipping. Nobody notices in code review because code review does not spawn the process and send it bytes. The person who notices is a developer three weeks later, staring at a hung tool call with no idea whether the bug is in their agent, their network, or the MCP server they installed from someone else's GitHub repo.

## Why I built it

I looked at what exists already for MCP tooling and found supervisors that sit in front of a server and restart it when it hangs, and profilers that read a JSONL transcript after the fact and tell you which method was slow. Both are useful and neither answers the question I actually wanted answered before I trusted a server: does this thing implement the stdio transport correctly in the first place. A supervisor papers over a broken handshake by restarting the child. A profiler can only see the traffic that already happened; it cannot provoke the specific edge case that breaks a naive implementation.

What I wanted was closer to a compatibility test suite you would run once against a candidate server, the same way you would not ship a database driver without running it against the reference protocol's own test corpus. Something that actively sends the garbage input, the oversized payload, the fragmented write, the notification a server should ignore, and reports pass or fail for each one, with a process exit code a CI job can gate on.

Perl turned out to be the right tool for exactly this job and not because of nostalgia. Every check here needs precise control over raw bytes on a pipe: non blocking reads with a real deadline, writes split into three byte chunks with a sleep in between, a hard ceiling on how much unparsed data the auditor itself will buffer before giving up. `IPC::Open3`, `IO::Select`, `sysread` and `syswrite` give you that control directly, and they have shipped in core Perl since long before Docker existed. There is no package manifest, no virtualenv, no npm install. You copy one file onto a box that already has `perl` on it, which is to say almost any Linux server, any macOS laptop, any CI image, and you can audit an MCP server without installing anything else first.

## When to use it

- Before you add a third party MCP server to your team's default agent configuration, so you find out about a broken shutdown handshake before your CI runners start accumulating orphaned processes instead of after.
- While you are building your own MCP server, as a fast local check that catches the stdout pollution and multi line JSON bugs that are otherwise invisible until a real client trips over them.
- In CI, as a gate on a server package: run the auditor against the packaged binary or script on every change, fail the build on any FAIL finding, and catch a regression before it reaches a release.
- When an agent framework reports a mysterious hang or a tool result that clearly does not match the tool that was called, to rule the transport layer in or out before you go looking for the bug somewhere more complicated.
- When you maintain a server in a language whose ecosystem has no MCP conformance tooling of its own; this treats the server as a black box over stdio, so the implementation language is irrelevant.

## How it works

The auditor spawns your command with `IPC::Open3::open3` inside `MCA::Session::spawn`, which keeps the three pipes and puts every handle into `:raw` binmode so no PerlIO layer quietly rewrites line endings or reinterprets bytes underneath the auditor's own framing logic. Everything downstream operates on that one `MCA::Session` object.

Reading is built around `read_line`, which pulls chunks off the child's stdout with `sysread` inside an `IO::Select` loop, appends them to an internal buffer, and returns the first complete line up to `HARD_LINE_CAP` (64MB) as a safety ceiling so a runaway server cannot make the auditor itself exhaust memory. `read_message` wraps that with UTF-8 decoding and a `JSON::PP` decode attempt; if the first line does not parse, it stitches on up to four more lines before giving up, which is exactly how the multi line pretty printed JSON bug gets caught: the auditor either successfully reassembles the message, in which case it flags the `multiline` result so `framing.single_line_per_message` records a FAIL, or it never manages to reassemble it, in which case the handshake itself fails outright. Every line the child ever writes to stdout is also appended to `all_raw_lines`, which is what `purity.stdout_is_jsonrpc_only` walks at the very end to catch any line, anywhere in the whole session, that is not a well formed JSON-RPC 2.0 object.

Writing goes through `send_line`, `send_raw` and `send_fragmented`. The last one is the one doing real work for `resilience.fragmented_write`: it writes a valid request in three byte slices with a ten millisecond sleep between each `syswrite`, because a pipe read is never guaranteed to hand back a full line in one call, and a server that assumes it will breaks the moment traffic gets slow or chunked, which happens constantly once you put a real transport (SSH, a container runtime, a slow disk) between client and server instead of a same host pipe. `drain_stderr` runs opportunistically inside every read loop with a zero second `IO::Select` poll so a chatty child's stderr pipe never fills up and stalls it while the auditor is busy waiting on stdout.

The checks themselves run as one linear sequence against a single spawned session, matching how a real client actually uses one: `handshake.silence_before_init` reads with a short deadline before anything is sent, `handshake.initialize_ok` sends a real `initialize` request and validates the `protocolVersion` and `capabilities` fields come back with a matching id, then `framing.utf8_validity`, `framing.no_bom` and `framing.single_line_per_message` all run against that captured frame. `handshake.initialized_notification`, `error_handling.unknown_method_request`, `error_handling.unknown_notification_silent` and `error_handling.malformed_json_recovers` probe JSON-RPC semantics the server is supposed to honor regardless of which capabilities it declares. `concurrency.pipelined_requests` fires three `tools/list` calls back to back before reading any response, which is the fastest way to expose a server that can only read after it finishes writing and will therefore deadlock the moment its output pipe fills. `resilience.oversized_message` pads a `tools/call` request out to two megabytes by default (`--max-payload`) to catch a fixed size read buffer. `lifecycle.stdin_eof_clean_exit` closes the child's stdin, waits up to `--shutdown-timeout` seconds, and escalates through SIGTERM then SIGKILL via `reap_hard` if the process refuses to leave, which is also exactly what runs from the `cleanup` handler if you Ctrl-C the auditor itself, so a broken server under test can never outlive the tool auditing it. If `initialize` never succeeds, every check that depends on a live session is recorded as SKIP with an explicit reason instead of producing a page of confusing secondary failures. Command execution never goes through a shell; `@cmd` is passed straight to `open3` as a list, so there is no argument splitting or injection risk from whatever command line you point the auditor at.

Every check records a status of PASS, WARN, FAIL or SKIP through `record`, and the process exit code follows from the worst status seen: 2 if anything FAILed, 1 if only WARN findings exist and `--strict` was passed, 0 otherwise, which is what makes it usable directly as a CI gate.

## Usage

```
perl McpStdioConformanceAuditor.pl [options] -- <server-command> [args...]
```

Everything after `--` is executed exactly as given, with no shell involved. Common options: `--timeout=SEC` for the per read deadline (default 5), `--startup-timeout=SEC` for the before-init silence window (default 2), `--shutdown-timeout=SEC` for how long a clean exit gets after stdin closes (default 5), `--max-payload=BYTES` for the oversized message probe size (default 2000000), `--protocol-version=STR` to change what `initialize` advertises, `--only=id,id` or `--skip=id,id` to run or exclude specific checks by their dotted id (for example `concurrency.pipelined_requests`), `--strict` to make a WARN also fail the build, `--json` to print a machine readable report instead of the text table, and `--verbose` to echo every raw frame sent and received to stderr while debugging. Two examples:

```
perl McpStdioConformanceAuditor.pl -- node my-server.js
perl McpStdioConformanceAuditor.pl --strict --json -- python3 -m my_mcp_server
```

## Notes

This audits the stdio transport only; it has nothing to say about whether your tool implementations return correct results, only about whether the protocol plumbing underneath them is sound. It assumes a POSIX environment with real pipes, so it runs on Linux and macOS and is not expected to work as is on Windows, where pipe and select semantics differ enough that the timing based checks would need a different implementation. It also assumes your server accepts `tools/list` even if it has no tools (returning a method not found error is treated as a valid, correlated response for the concurrency check, since the point there is transport correctness, not capability coverage). The oversized message and malformed JSON checks intentionally send input a well behaved client would never produce; that is the point of an adversarial harness, and a server that only handles the happy path is exactly what this is meant to catch before your users do.
